## What runs where
```
git push to main ──► CI (lint, tests, scanners, Docker build)
                          │ success
                          ▼
              deploy.yml  (GitHub Environment "production": a reviewer approves)
   OIDC token ──► IAM role credit-risk-github-deploy   (no AWS keys stored anywhere)
                          │
   dvc pull model ─► docker build (model baked in) ─► Trivy ─► ECR  credit-risk-api:<git SHA>
                          │
          register task-definition revision ─► ECS service credit-risk-api (Fargate, 1 task)
                          │ wait stable
                          ▼
            smoke test: /health, /predict without key = 401, /predict with key = score
                 fail ► point the service back at the previous revision
```

## Services used (and why)
| Service | Resource | Notes |
|---|---|---|
| ECR | repository `credit-risk-api` | Tags are immutable (one SHA, one image); scan on push; keeps the 20 newest images |
| ECS on Fargate | cluster `credit-risk`, service `credit-risk-api`, task 0.25 vCPU / 0.5 GB, desired count 1 | No EC2 to manage; the deployment circuit breaker rolls back a revision whose tasks never become healthy |
| VPC (existing default VPC) | security group `ServiceSecurityGroup` | Inbound **8000 only, from one CIDR you choose**. No load balancer and no NAT gateway (cost) |
| Secrets Manager | secret `credit-risk-api/api-key` | Generated by AWS (40 characters); injected into the container as `API_KEY`; never in git |
| CloudWatch Logs | log group `/ecs/credit-risk-api`, 14 days | JSON request log (request id, route, status, latency, model version; no payloads) |
| CloudWatch alarms + SNS | `credit-risk-api-5xx`, `credit-risk-api-p95-latency` → topic `credit-risk-api-alerts` → e-mail | Metrics come from log metric filters because there is no load balancer |
| S3 | artifact bucket (encrypted, private, TLS only) | `models/` (task role reads), `prediction-logs/` (30-day expiry), `monitoring-reports/` (90 days) |
| IAM | `credit-risk-api-execution`, `credit-risk-api-task`, `credit-risk-github-deploy`, GitHub OIDC provider | See below |
| AWS Budgets | `credit-risk-monthly` (default US$10), **optional** | A project budget already exists (created in the Billing console, 2026-11-08, per `memory.md`), and `rules.md` §8 wants it before anything billable. `CREATE_BUDGET=true` adds this template's own (e-mail at 80 % actual, 100 % forecast) |

Everything is created with CloudFormation (two stacks) so that teardown is a deletion, not a hunt. All stacks are tagged `project=credit-risk`.
Everything is in one Region (the project Region, read from the CLI profile; `ap-southeast-2` here). Nothing uses another Region.

## IAM (least privilege)
All policies are written inline in [`service.yaml`](../infra/aws/cloudformation/service.yaml); there is no `*:*` and no `Resource: "*"` except where AWS offers no resource-level permission (listed).

| Role | May do | Cannot do |
|---|---|---|
| **Execution role** (`credit-risk-api-execution`) | pull from the one ECR repository; write the one log group; read the one secret | anything else |
| **Task role** (`credit-risk-api-task`) | read `s3://<bucket>/models/*`; write `s3://<bucket>/prediction-logs/*`; write the log group | list buckets, read other prefixes |
| **GitHub deploy role** (`credit-risk-github-deploy`) | push to the one ECR repository; register task definitions (no resource-level permission exists); update **only** the service `credit-risk/credit-risk-api`; `iam:PassRole` for **only** the two roles above and only to `ecs-tasks.amazonaws.com`; read the one secret (smoke test); add/remove one ingress rule on the one security group (the runner's address, during the smoke test); read DVC remote objects under `dvc/` | create or delete clusters, roles, buckets; touch other services |

**Trust:** only OIDC tokens issued for `repo:Hashir-Rauf/Credit-Risk-Intelligence-Platform:environment:production`, audience `sts.amazonaws.com`.
GitHub now puts the numeric owner and repository IDs into the subject (`repo:Hashir-Rauf@172579469/Credit-Risk-Intelligence-Platform@1447265046:environment:production`); the first live run failed with `AccessDenied` until the role trusted that form (found by reading the subject in CloudTrail). The template takes `GitHubOwnerId` and `GitHubRepoId` and accepts both forms.
Jobs that run in a GitHub Environment present the *environment* as their subject, not a branch. So the branch restriction is enforced on the
Environment itself (below): a job can only run in `production` if the workflow ran from `main`.

## Web frontend on AWS
The Next.js frontend runs as a **second, non-essential container in the same ECS task** as the API (task size 0.5 vCPU / 1 GB), so there is one task, one public IP and no load balancer.
* The browser talks only to the frontend (port 3000). Its server side calls the API on `127.0.0.1:8000` inside the task and attaches the API key from the same Secrets Manager secret; the key never reaches the browser.
* Port 3000 is open to the operator CIDR by default. The frontend holds the API key, so opening it widens who can score customers; the `FrontendCidr` parameter (`FRONTEND_CIDR=` for `setup.sh`) opens **only this port** to another range, for example `0.0.0.0/0` for a deliberate public demo (2026-11-27 it was opened that way; the API port 8000 stays on the operator range). Revert with `FRONTEND_CIDR=` empty. The API's rate limit (600 requests/minute per client) still applies.
* Image: its own ECR repository `credit-risk-frontend` (immutable tags, created by the bootstrap stack). The Deploy workflow builds, Trivy-scans and pushes it next to the API image and `scripts/aws_ecs_deploy.sh` adds the `frontend` container when it registers the new task revision; the smoke test also checks the frontend (`/api/health` must see the API, `/` must render the form).
* The container is non-essential: if it crashes, the scoring API keeps running (ECS restarts it).
* `infra/aws/endpoint.sh` prints the API URL on the first line and the frontend URL on stderr.
* The placeholder task definition in `service.yaml` is deliberately unchanged (editing it would reset the service); the frontend container exists only in the revisions that the deploy script registers.

## Risk to confirm first: the GitHub OIDC provider may be blocked
`memory.md` ("AWS findings, 2026-11-08") records that a service control policy **explicitly denies `iam:ListOpenIDConnectProviders`**, so creating the GitHub OIDC provider is probably blocked too. It has not been tried (nothing creates cloud resources without your go-ahead). `service.yaml` creates the provider; if that fails, the stack rolls back cleanly and nothing is left behind.
Options if it is blocked: (1) ask the AWS project owner to allow `iam:CreateOpenIDConnectProvider` for `token.actions.githubusercontent.com`; if the provider exists already, run with `CREATE_OIDC_PROVIDER=false` and pass its ARN as `ExistingOidcProviderArn`; (2) deploy with a short-lived key a person creates by hand for the demo (this breaks the "no stored AWS keys" exit criterion, so it needs the instructor's agreement). Do not store a long-lived key in GitHub to make this pass.

## One-time setup (ordered)
Do these steps in order. Steps marked ($) create billable resources.

1. **Check the plan and Region.** `aws freetier get-account-plan-state` and `aws configure get region`. ECS/Fargate, ECR, CloudFormation, SNS, Secrets Manager, CloudWatch and Budgets must be available on the project's plan (see AWS Settings for the supported-services list).
2. **Sign in:** `aws login` (or SSO) and select the profile: `export AWS_PROFILE=credit-risk`.
3. **Find your public IP:** `curl -s https://checkip.amazonaws.com`. This is the only address that can reach the API.
4. **Create the foundation** ($, small): `ALERT_EMAIL=you@example.org ALLOWED_CIDR=<ip>/32 ./infra/aws/setup.sh`.
   It creates the foundation stack (ECR, bucket, log group, secret, topic; a budget only if asked), then the ECS service stack with **desired count 0** (nothing runs yet), and prints the values to set in GitHub.
   `CREATE_OIDC_PROVIDER=false` if the project already trusts GitHub Actions.
5. **Confirm the SNS e-mail** (and the budget e-mail). Unconfirmed subscriptions receive nothing.
6. **GitHub repository variables** (Settings → Secrets and variables → Actions → Variables): `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN`, `AWS_SERVICE_SG_ID` (printed by `setup.sh`), and for promotions `MLFLOW_TRACKING_URI`. Secrets: `MLFLOW_TRACKING_USERNAME`, `MLFLOW_TRACKING_PASSWORD` (a DagsHub token; used only when promoting a registry model).
7. **GitHub Environment `production`** (Settings → Environments): *Required reviewers* = a teammate (or you, plus a second approver for the demo); *Deployment branches* = `main` only. This is the manual promotion gate, and it is what the AWS trust policy keys on.
8. **Deploy** ($): merge to `main`, wait for CI, approve the `production` deployment. First deployment scales the service from 0 to 1.
9. **Find the endpoint and key:** `./infra/aws/endpoint.sh --key` prints `http://<public-ip>:8000` and the API key (the key is only printed when you ask).

```bash
KEY=$(./infra/aws/endpoint.sh --key | tail -1);  URL=$(./infra/aws/endpoint.sh | head -1)
curl -s "$URL/health"
curl -s -X POST "$URL/predict" -H "X-API-Key: $KEY" -H "Content-Type: application/json" -d @scripts/sample_predict.json
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$URL/predict" -H "Content-Type: application/json" -d @scripts/sample_predict.json   # 401
```

## Deploy and the quality gates
* `deploy.yml` starts only from a **successful CI run on `main`** (`workflow_run`). A failing CI, including the model quality-gate tests, means no deployment. The workflow also refuses a model whose `reports/evaluation.json` says `gate.passed: false`.
* Build → **Trivy** (HIGH/CRITICAL with a fix fail the run) → push the image tagged with the **git SHA** (never `latest`) → new task-definition revision → service update → wait stable → smoke test.
* The smoke test opens the port for the runner's address only for the duration of the test and removes it afterwards, even if the test fails.
* A failed wait or smoke test points the service at the previous revision automatically (`scripts/aws_ecs_deploy.sh`).

## Rollback
* **Automatic:** the circuit breaker and the smoke-test rollback above.
* **Manual:** Actions → *Rollback* → `target` = `previous` (default), a revision number, or a git SHA. The same `production` approval applies; the service is pointed at that revision and smoke-tested again. [`scripts/aws_rollback.sh`](../scripts/aws_rollback.sh) does the work.
* **Model rollback** (registry alias and the deployed model together): see [promotion-rollback.md](promotion-rollback.md).

Rehearse it once and keep the run log as evidence.

## Alarms (and triggering them on purpose)
| Alarm | Source | Fires when | How to trigger it once |
|---|---|---|---|
| `credit-risk-api-5xx` | metric filter on the JSON log (`status >= 500`) | any 5xx in a minute | Deploy a revision whose `MODEL_PATH` is wrong, or temporarily set the task's `MODEL_PATH` to a missing file: `/predict` answers 503 |
| `credit-risk-api-p95-latency` | metric filter on `duration_ms`, p95 | p95 > 500 ms in 2 of 3 minutes | Send many concurrent 100-record `/predict` or `/explain` calls from the allowed IP (Fargate 0.25 vCPU saturates quickly) |

Both notify the SNS topic on entering ALARM and on recovery (OK). Save the e-mail and the alarm history page as evidence. A CloudWatch Logs Insights query for errors:
`fields @timestamp, route, status, duration_ms, request_id | filter status >= 500 | sort @timestamp desc | limit 50`.

## Teardown (and proof)
The full ordered clean-up (AWS, GitHub, local, what to check afterwards) is in the README section "Clean up".

```bash
./infra/aws/teardown.sh --yes
```
It scales the service to 0, deletes the service stack, deregisters and deletes every task-definition revision, empties the bucket, deletes the foundation stack (the ECR repository is emptied with it), force-deletes the secret (no recovery window, so no billing and the name is free), then **lists what is left** (stacks, clusters, ECR, secrets, log groups, buckets) — all should be empty.
Confirm in the console (ECS, ECR, S3, CloudWatch, Secrets Manager, CloudFormation) and keep a screenshot. After a teardown, rerun `setup.sh` to start again.

## Known limits (accepted, and why)
* **HTTP, not HTTPS.** An ALB with a certificate needs a domain and costs more than the whole service. Mitigations: the security group admits one IP, the API key is 40 random characters, and the only data in transit is simulated coursework data. For anything real, put the service behind an ALB or CloudFront with TLS.
* **The public IP changes on every deployment** (no load balancer / Elastic IP). Use `infra/aws/endpoint.sh`.
* **One task, no high availability.** A replacement task starts on failure; there is a short gap.
* The prediction log lives on the task's ephemeral disk and is exported to S3 every 5 minutes when `PREDICTION_LOG_S3_URI` is set; the last few minutes are lost if the task dies.
